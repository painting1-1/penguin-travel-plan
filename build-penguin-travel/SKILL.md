# 跟小企鹅一起出发吧

让大家都跟小企鹅一起出发。为每位使用者生成自己的旅行页面，不访问原作者私人网站、数据和账号。

## 工作流程

1. 明确目的地、日期、人数及确定的交通住宿。复用用户提供的信息，只问影响路线的关键缺项。没有信息时使用明确标注的虚构示例。
2. 阅读 [设计规则](references/design.md)、[功能规则](references/product.md) 与 [板块契约](references/sections.md)，制作记账时同时阅读 [记账规则](references/ledger.md)。包含记账时必读 [记账结构与算法](references/ledger.md)。涉及公开、部署、登录、云同步时，再阅读 [发布与隐私](references/privacy-and-publishing.md)。
3. 新建页面先阅读 [模板与资料替换](references/template.md)，运行 `python3 scripts/scaffold.py --output <新目录>` 复制完整可运行模板。主要替换 trip-data.json 并按 [封面指令](references/design.md#目的地封面指令) 根据目的地自动生成封面，复用现有布局与交互；layout-example.html 仅辅助理解，不能代替成品。既有页面仅合并需要的资源，禁止重建覆盖。
4. 默认制作一张从上到下连续滚动的长网页，按封面→旅行概览与交通住宿→每日行程→行李→必买→待办→记账排列。顶部五个导航只滚动定位，不隐藏其他主要板块。仅每日日期和记账内部允许局部切换。用户只需部分时从其要求，既有页面保留框架。没有项目时可用 HTML/CSS/JS；明确要求单文件时内联样式与脚本，图标可作为相邻文件交付。
5. 核对动态事实，优先店铺、运营方与旅游机构。无法核实就写“待确认”，不编造营业、价格、船班、坐标和转场耗时。研究依据保留在开发记录，默认不显示在紧凑行程卡片中。
6. 默认交付可本地运行、能在浏览器保存数据的版本。有发布能力的平台按使用者的明确发布要求直接发布，不重复索取确认；未要求发布则交付预览。修改旧站先说明方案、确认后执行；“直接执行”或明确确认不再问一次。修改同步标题、正文、提醒、导航、地图点位与相关待办顺序。默认功能以功能规则为准，不把讨论过但未实现的功能加入模板。
7. 先运行资料验证与项目记账测试，再按 [验收清单](references/qa.md) 测试，修复再交付。使用者已明确要求生成并发布时，视为发布授权；额外创建公开源代码仓库、发送或预订仍须对应授权。没有发布能力时说明限制并交付完整可运行项目，不声称已上线。

## 资源

- `assets/template/`：完整网页、通用封面、企鹅图标、示例资料、本地保存、地图、记账和原币结算、预览与测试。默认以此为制作起点。
- `scripts/scaffold.py`：复制完整模板，拒绝覆盖非空目录；支持 `--data` 传入自己的资料。
- `scripts/validate_trip.py`：检查时间、稳定ID、路线/人员引用及资料字段。
- `references/template.md`：替换资料、已有数据保留与运行方法。
- `assets/layout-example.html`：仅辅助理解组件位置，不是默认生成入口。
- `assets/theme.css`：补充品牌变量；完整页面样式在模板里。
- `LICENSE`：自有代码及企鹅采用 MIT；模板的第三方组件许可见 `assets/template/THIRD_PARTY_NOTICES.md`。

## 硬约束

- 不把原作者当作所有人的本人。选择本人并保存稳定人员 ID；未选择时显示提示。
- 主指标“我的旅行花费”只计本人承担份额，不混加个人与团队支出，不把替别人垫付当消费。
- 不把本地保存宣称为跨设备云同步。
- 不把前端 PIN 弹窗宣称为安全防护；需要访问保护就用服务端验证。
- 不泄露订单、真实邮箱、账单、密码、连接配置、私有地址和提交历史。
- 不为紧凑排版隐藏必须预约、取回行李、发车缓冲等约束；只合并重复文案。
